## 1. 개요

이 문서는 Claude Code가 ‘앵커 사업비 지침 안내 챗봇’을 만들 때 그대로 따를 기능 명세다. 기존 제미나이 프로토타입(‘스마트 앵커 어시스턴트’)의 기능을 유지하고, 정제한 Q&A 데이터를 찾아 답하는 검색형 구조와 운영 기능을 더한다.

- **목적**: 앵커 사업비 집행 문의에 ‘재단이 이미 낸 답’과 ‘지침·FAQ’에 근거해 즉시 답하고, 근거가 없거나 판단이 필요한 질문은 담당 기관으로 연결한다.
- **운영 주체**: 한국연구재단 RISE지원팀(중앙앵커센터). 운영자는 개발자가 아니므로 데이터 갱신·프롬프트 수정은 모두 관리자 화면에서 코드 없이 할 수 있어야 한다.
- **사용자 확대 단계**: 1단계 재단 내부 → 2단계 17개 시도 앵커센터 → 3단계 전체 참여대학. 최종적으로 앵커성과관리플랫폼에 올린다.
- **답변 범위**: ① 앵커 사업비 집행 및 관리 지침 ② 지침 FAQ ③ 지침 해석·적용(재단 기존 답변). 법령 유권해석, 집행 (불)인정 판단, 성과관리(실적 인정·자체평가)는 답하지 않는다.
- **제약**: 비용 최소화. 로그인 정보 외 개인정보를 받지 않는다. 데이터는 현재 674건이나 2,000건까지 늘어도 구조를 바꾸지 않고 돌아가야 한다.

## 2. 시스템 구성

질문은 서버에서 개인정보를 가린 뒤, 표준 Q&A와 지침에서 관련 항목만 찾아 AI 모델에 넘긴다. 모델은 답변과 함께 답변 유형을 돌려주고, 화면은 유형에 따라 근거 카드나 연결 버튼을 보여준다. 틀리거나 빈 답은 검토 대기함에 쌓이고, 관리자가 확정하면 바로 검색에 반영된다. API 키와 모델 호출은 모두 서버에서만 일어난다.

## 3. 지식 데이터

챗봇의 지식은 네 가지다. ‘항상 지키는 규칙’(답변 원칙)은 매 질문마다 모델에 넣고, 나머지는 질문과 관련된 항목만 검색해 넣는다. 모두 관리자 화면에서 엑셀 업로드로 교체할 수 있어야 한다.

| 지식 | 내용 | 현재 분량 | 모델에 넣는 방식 |
| --- | --- | --- | --- |
| 답변 원칙 | 담당자가 검수하며 정한 답변 원칙(범위, 연결 규칙, 인건비·수당·이월·정산 등 반복 기준) | 약 40개 항목, 5천 자 내외 | 시스템 프롬프트에 항상 포함 |
| 표준 Q&A | 대표 질의 + 통합 답안. 통합번호, 대분류(사업 유형), 중·소분류, 답변 변경 이력, 연결형 여부, 검수상태 포함 | 674건, 약 32만 자 | 질문마다 관련 상위 5\~8건만 검색해 포함 |
| 답변범위 외 목록 | 성과관리·실적 인정처럼 챗봇이 답하지 않는 유형의 대표 질의 | 19건 | 질문이 여기에 가까우면 ‘답변 대상 아님’ 안내 |
| 지침·FAQ 원문 | 현행 앵커 사업비 집행 및 관리 지침, FAQ | 파일 제공 후 산정 | 조항 단위로 쪼개 검색해 포함, 쪽수·조항 번호를 함께 저장 |

**표준 Q&A 업로드 규칙**

- 엑셀 ‘통합질의’ 시트 형식을 그대로 읽는다(통합번호·대분류·중분류·소분류·대표 질의·요지 체크리스트·통합 답안·연결형 답변·검수상태).
- 검수상태가 ‘확정’인 행만 서비스에 쓴다. ‘미검수’는 1단계(재단 내부) 시범운영에서만 쓸 수 있게 설정으로 켜고 끈다.
- 검색에는 ‘대표 질의 + 요지 체크리스트’를 쓴다. 하나의 통합 질의에 여러 요지가 들어 있어 대표 질의만으로는 검색이 놓칠 수 있기 때문이다.
- 업로드할 때마다 버전을 남기고, 이전 버전으로 되돌릴 수 있어야 한다.
- 개인정보는 이미 비식별 처리된 데이터만 올린다. 업로드 시 전화번호·이메일 패턴이 보이면 경고한다.

## 4. 기존 기능 (프로토타입에서 유지·개선)

제미나이 프로토타입(React 단일 파일)에 있던 기능은 모두 유지한다. 다만 브라우저 안에서만 돌던 구조를 서버·DB 구조로 옮기고, 문서를 통째로 넣던 방식을 검색형으로 바꾼다.

| 기능 | 기존 동작 | 새 버전에서 바뀔 점 |
| --- | --- | --- |
| 회원가입·승인 | 가입 신청 → 관리자 승인, 관리자 직접 생성 | 가입 시 소속 구분(재단/지역앵커센터/대학)·기관명·사업 유형만 받기. 연락처는 받지 않음 |
| 권한 | 사용자/관리자 권한 변경 | 사용자 · 관리자 2단계 (검수자 역할은 2026-11에 없애고 관리자에 합침) |
| 로그인 보안 | 10회 실패 시 잠금, 아이디로 비밀번호 초기화 후 강제 변경 | 유지. 비밀번호는 서버에 해시로 저장 |
| 대화 세션 | 사용자별 대화 목록 | 유지. 세션 제목 자동 생성, 검색 |
| 관리자 대화 열람 | 사용자 대화를 읽기 전용으로 열람 | 유지. 평가(Bad)·연결 답변만 필터링하는 기능 추가 |
| 1:1 문의함 | 사용자가 관리자에게 문의, 관리자 답변 등록 | 유지. 챗봇 답변 아래 ‘재단에 문의하기’로만 문의(챗봇을 거치지 않은 바로 문의 불가), 대화 내용 자동 첨부 |
| 지식 문서 업로드 | PDF/TXT/MD/CSV 다중 업로드(15MB), 문서별 AI 요약 | 엑셀(표준 Q&A) 업로드 추가. 업로드 후 조항 단위로 쪼개 검색 색인을 만듦. 매 질문마다 PDF 전체를 보내는 방식은 없앰 |
| 시스템 프롬프트 편집 | 관리자 화면에서 수정 | 유지. 변경 이력과 되돌리기 추가 |
| 답변 구조 | 질의요약 → 답변요약 → 상세 안내 → 유의사항 → 근거 규정, 고정 면책 문구 | 유지(6장 참조). 근거는 실제 검색된 항목만 표시 |
| AI 호출 | Gemini API, 지수 백오프 재시도 | 재시도 유지. 모델을 설정에서 바꿀 수 있게(제공사·모델명·API 키를 환경변수로). API 키는 서버에만 둠 |
| 다크모드 | 있음 | 유지 |

## 5. 추가 기능 (추천)

핵심은 세 가지다. ① 관련 표준답안만 찾아 답하는 검색형 답변, ② 답을 못 하거나 하면 안 되는 질문을 가려 연결하는 라우팅, ③ 틀린 답과 빈 곳을 모아 표준답안을 보완하는 운영 루프다. 우선순위는 ‘필수’가 1단계(재단 내부) 시범운영 전에 있어야 하는 것이다.

### 5-1. 답변 품질

| 기능 | 동작 | 우선순위 |
| --- | --- | --- |
| 검색형 답변 | 질문을 받으면 표준 Q&A와 지침 조항에서 관련 항목을 찾아(키워드 + 의미 검색 혼합) 상위 5\~8건만 모델에 넘긴다. 관련도가 기준값보다 낮으면 답을 만들지 않고 ‘근거 없음’으로 처리한다 | 필수 |
| 사업 유형 선택 | 대화 시작 시 ‘순수앵커·글로컬·의대교육·초광역·기타·모름’ 중 선택(가입 시 기본값). 검색 시 해당 사업 답안을 우선하고, 다른 사업 답안을 쓸 때는 그 사실을 밝힌다 | 필수 |
| 근거 표시 | 답변 아래 ‘참고한 근거’ 카드: 표준답안(통합번호·대표 질의, 펼치면 답안 전문), 지침(조항·쪽수, 펼치면 원문), FAQ 번호. 모델이 실제로 인용한 항목만 표시 | 필수 |
| 답변 변경 안내 | 근거 답안에 변경 이력이 있으면 “이 기준은 ○○년 ○월부터 적용됩니다”를 표시. 표시 여부는 관리자 설정 | 권장 |
| 자주 묻는 질문 | 첫 화면에 중분류별 대표 질문 버튼. 누르면 바로 질문 | 권장 |

### 5-2. 연결 라우팅 (답변 유형 판정)

모든 답변에 아래 네 유형 중 하나를 붙이고, 유형별로 화면 하단 버튼을 달리 보여준다. 유형은 로그에 남겨 통계에 쓴다.

| 유형 | 조건 | 화면 처리 |
| --- | --- | --- |
| 근거 답변 | 관련 표준답안·지침이 있고 결론을 낼 수 있음 | 답변 + 근거 카드 |
| 연결형 | 근거 답안이 연결형이거나, 개별 사안·(불)인정 판단·법령 해석을 요구함 | 원칙만 안내 + 연결 대상 표시(지역앵커센터 / 대학 내부 규정 / e나라도움 콜센터 / 교육부). 연락처는 보여주지 않고 ‘지역앵커센터에 문의하시기 바랍니다.’처럼 문의처만 안내 (2026-11 결정) |
| 답변범위 외 | 성과관리·실적 인정 등 답변범위 외 목록과 가까운 질문 | “사업비 지침 챗봇의 답변 범위가 아닙니다” + 담당 부서 안내 |
| 근거 없음 | 검색 결과가 기준값 미만 | 추측하지 않고 ‘재단에 문의하기’ 버튼(1:1 문의함으로 대화 자동 첨부). 질문은 검토 대기함으로 |

## 6. 답변 생성 규칙

모델은 검색된 근거와 답변 원칙 안에서만 답한다. 아래 규칙을 시스템 프롬프트의 기본값으로 넣고, 관리자가 수정할 수 있게 한다.

**답변 구조** (기존 프로토타입 유지)

1. 질의 요약: 사용자가 물은 것을 한 줄로
2. 답변 요약: 결론 먼저(가능 / 불가 / 지역앵커센터 확인 필요 / 답변 범위 아님)
3. 상세 안내: 근거 답안·지침의 원칙을 질문 상황에 대입해 설명
4. 유의사항: 예외, 사업 유형별 차이, 기준 변경 시점
5. 근거: 인용한 통합번호·지침 조항 (화면에서는 근거 카드로 표시)
6. 고정 면책 문구: “본 답변은 사업비 지침과 기존 질의응답에 근거한 안내이며, 구체적인 집행 인정 여부는 상위보조사업자(지역앵커센터)의 판단에 따릅니다.”(문구는 관리자 수정 가능)

**해야 할 것**

- 근거에 있는 내용만 쓴다. 여러 표준답안을 조합할 때 서로 다른 사업 유형의 답을 섞지 않는다.
- 재단 공식 문체(\~입니다/\~합니다)를 쓴다. 문장은 짧게, 결론 먼저.
- 질문이 여러 개면 번호를 매겨 각각 답한다. 답할 수 없는 부분은 그 부분만 연결한다.
- 사용자가 사업 유형을 선택하지 않았고 사업에 따라 답이 다르면, 답하기 전에 어느 사업인지 한 번 물는다.

**하지 말 것**

- 근거 없이 추측하기. “가능할 것으로 보입니다”류로 결론을 만들지 않는다.
- 개별 집행 건의 (불)인정 판단, 예외 승인.
- 법령(국가계약법·보조금법·혁신법 등) 유권해석. 해당 법령을 따르도록만 안내한다.
- 명문화되지 않은 해석 변경이나 ‘검토 중’인 사항 언급.
- 특정 대학·기관·개인 이름 언급(표준답안에 있더라도).

**모델 출력 형식**

화면이 근거 카드와 연결 버튼을 그릴 수 있도록, 모델은 본문과 함께 아래 항목을 구조화해서 돌려주게 한다.

```json
{
  "answer_type": "근거답변 | 연결형 | 답변범위외 | 근거없음",
  "business_type": "순수앵커 | 글로컬 | 의대교육 | 초광역 | 기타 | 공통",
  "answer_markdown": "답변 본문",
  "cited_qa_ids": ["B4-01-a"],
  "cited_guideline": [{"clause": "조항", "page": "쪽수"}],
  "referral": "지역앵커센터 | 대학규정 | e나라도움 | 교육부 | 담당자 | null"
}
```

## 8. 비기능 요구사항

- **보안**: API 키는 서버 환경변수에만 둔다(브라우저에 노출 금지). 비밀번호는 해시 저장, 세션은 만료 시간 설정. 모든 관리자 기능은 서버에서 권한을 다시 확인한다.
- **개인정보**: 가입 시 연락처·실명을 받지 않는 것을 기본으로 한다. 질문의 개인정보 패턴은 모델에 보내기 전에 가린다. 대화 보관 기간을 설정으로 정하고 지난 것은 자동 삭제한다.
- **비용**: 질문당 모델에 넣는 양을 ‘답변 원칙 + 검색 상위 5\~8건 + 최근 대화 몇 턴’으로 제한한다. 모델은 설정에서 바꿀 수 있게 하고, 가벼운 모델로 시작해 평가 질문집 점수를 보고 올린다. 사용자별·전체 일일 상한을 둔다.
- **확장성**: 표준답안 2,000건, 지침 개정판 여러 개에서도 검색이 1초 안팎으로 돌아야 한다.
- **로그**: 답변마다 검색된 항목, 답변 유형, 토큰·비용, 응답 시간을 남긴다. 검토 대기함과 통계가 이 로그를 쓴다.
- **장애 대응**: AI 호출 실패 시 지수 백오프 재시도 후, 실패하면 “잠시 후 다시 시도”와 1:1 문의 버튼을 보여준다.
- **배포**: 1단계는 재단 내부에서 쓸 수 있는 단일 서버(또는 클라우드)로 충분하다. 앵커성과관리플랫폼 연동(로그인 연동, 화면 삽입)은 3단계에서 플랫폼 운영 측과 협의해 정한다.
- **접근성**: 모바일에서도 챗 화면이 깨지지 않아야 하고, 다크모드를 유지한다.

## 9. 개발 순서와 Claude Code에 맡기는 방법

한 번에 다 만들게 하지 말고, 단계마다 돌아가는 것을 확인하며 넘어간다. 각 단계 끝에 직접 로그인해 질문 몇 개를 던져 보고 다음으로 간다.

1. **기반**: 로그인·가입 승인·권한, 대화 화면, AI 호출(서버 경유). 기존 프로토타입 화면을 최대한 살린다.
2. **지식 적재와 검색**: 엑셀(표준 Q&A)·답변 원칙 업로드, 검색 색인, 검색형 답변, 근거 카드. (지침·FAQ는 파일이 준비되면 같은 방식으로 추가)
3. **라우팅·안전장치**: 답변 유형 4종, 연결 버튼과 연락처, 개인정보 가림, 일일 상한.
4. **평가**: 평가 질문집 실행 화면. 여기서 점수가 기준을 넘어야 1단계 시범운영을 시작한다.
5. **운영 루프**: Good/Bad, 검토 대기함, 표준답안 편집기, 사용량·비용 화면.
6. **마무리**: 지침 개정 공지, 감사 로그, 배포 설정, 운영 설명서(비개발자용).

**Claude Code에 넘길 자료**

- 이 기능설명서(마크다운으로 내보내기)
- 기존 프로토타입 React 파일
- 표준 Q&A 엑셀(최신 검수본), 답변 원칙 문서, 답변범위 외 목록
- (있으면) 현행 지침·FAQ 파일, 평가 질문집

**첫 지시문 예시**

```text
이 폴더의 '앵커 사업비 챗봇 기능설명서.md'를 먼저 끝까지 읽어줘.
나는 개발자가 아니야. 코드를 짜기 전에 아래 두 가지를 먼저 보여줘.
1) 기술 구성 제안: 비용이 가장 적게 드는 방법으로, 서버·DB·검색·AI 모델을 각각 무엇으로 할지와 월 예상 비용
2) 설명서 9장 개발 순서를 기준으로 한 단계별 작업 계획
기존 프로토타입(smart_anchor_assistant.jsx)의 화면과 기능은 최대한 살려줘.
내가 계획을 승인하면 1단계부터 만들고, 단계가 끝날 때마다 내가 직접 확인할 수 있는 방법(실행 방법, 눌러볼 화면)을 알려줘.
API 키는 코드에 직접 넣지 말고 .env로 빼줘.
```

이후 단계마다 “설명서 5-2 연결 라우팅을 만들어줘”처럼 장 번호로 지시하면 된다.

## 10. 결정이 필요한 사항

- [ ] **AI 모델 제공사**: 기존 Gemini를 유지할지, Claude로 바꿀지. 설계는 둘 다 가능하게 해두고 평가 질문집 점수와 비용을 보고 정하는 것을 권한다.
- [ ] **설치 위치**: 재단 내부 서버인지 외부 클라우드인지. 외부 AI API로 질문을 보내는 것에 대한 재단 보안·정보화 부서 허용 여부 확인이 필요하다.
- [ ] **미검수 답안 사용 범위**: 1단계 내부 시범에서 ‘미검수’ 표준답안까지 쓸지, ‘확정’만 쓸지.
- [ ] **답변 변경 이력 표시**: 챗봇이 “○년 ○월부터 기준이 바뀜”을 사용자에게 보여줄지.
- [x] **연결 대상 연락처**: 노출하지 않음. 문의처 이름만 안내하고, 확인이 필요하면 챗봇의 1:1 문의함으로 받는다.
- [ ] **평가 통과 기준**: 1단계 시범운영을 시작할 최소 적중률(예: 평가 질문 100건 중 바른 표준답안 인용 80건 이상, 잘못된 결론 0건).
- [ ] **대화 보관 기간**: 개인정보·기록물 기준에 맞춘 보관 기간.
